# file_watcher_poll_utils

Polls a fixed set of filesystem paths and reports creation, modification, and deletion events by comparing `stat` signatures between calls.

## Usage

```python
from file_watcher_poll_utils import PollingFileWatcher, FileEvent

watcher = PollingFileWatcher(["/tmp/report.csv", "/tmp/queue.json"])
watcher.prime()  # record current state; do not report existing files

# ... later, on a timer or in a loop ...
for event in watcher.poll():
    print(event.path, event.event_type.value, event.signature)
```

`poll()` returns a list of `FileEvent` objects in the same order the paths were given to the constructor.  `FileEvent` has three fields: `path`, `event_type` (a `FileEventType` enum member), and `signature` (a `(st_mtime_ns, st_size)` tuple for created/modified events, `None` for deleted events).

## Why this exists

Most file-watching libraries bind to platform notification APIs (inotify, kqueue, FSEvents, ReadDirectoryChangesW).  Those are efficient but they are also the reason a watch library is hard to deploy: each backend has its own failure modes, its own event coalescing rules, and its own idea of what counts as a rename versus a delete-plus-create.  This library makes the opposite trade: it does no notification at all, just a cheap `os.stat` per path per poll.  The cost is latency (you see changes on your next poll, not immediately) and CPU proportional to the number of paths.  The benefit is that it behaves identically everywhere Python runs, needs no privileges, and can watch paths that do not exist yet.

## The awkward edge

The first call to `poll()` reports every path that currently exists as `created`, because the watcher has no prior state to compare against.  If you want to observe only changes that happen after you start watching, call `prime()` first.  `prime()` records the current signatures and discards any events that would have been generated by the initial scan.  There is no way to recover those initial events after priming; if you need them, skip `prime()` and handle the first batch yourself.

A second edge: the signature is `(st_mtime_ns, st_size)`.  A file that is rewritten with the same size within the same filesystem timestamp tick will not be reported as modified.  This is the standard trade-off for stat-based watchers and is why the signature is exposed on the event: callers who need stronger guarantees can hash the file contents when they see a signature they care about.

## API

- `PollingFileWatcher(paths)` — construct with any iterable of path strings.  Duplicates are collapsed while preserving first-seen order.
- `watcher.paths` — tuple of the observed paths in construction order.
- `watcher.prime()` — record current state without emitting events.
- `watcher.poll()` — return a list of `FileEvent` for changes since the last poll (or since construction, if `prime()` was not called).
- `FileEvent` — frozen dataclass with `path`, `event_type`, and `signature`.
- `FileEventType` — enum with `CREATED`, `MODIFIED`, and `DELETED` members (importable from `file_watcher_poll_utils.core`).
